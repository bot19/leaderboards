# 0.3.4: Deleted User stuck on onboarding

Implement this by following `docs/agents/build-docs.md`.

**Version:** 0.3.4

**Status:** ready-for-agent

**Blocked by:** 0.3.3

**What to build:** A fix. When a User is deleted (for example by the Super admin) while their browser still holds a session, the app sends them to `/onboarding`, saving a display name fails because the User no longer exists, and they can't leave without clearing localStorage by hand. After this fix, the app checks the session with the server on load and signs a deleted User out to `/login`. Onboarding also gets a Sign out link, so nobody can get stuck there again.

**food-friends reference:** None. food-friends doesn't check the session on load.

**Schema:** None.

### Why it happens

`AuthProvider` trusts the session `getSession()` reads from localStorage. That read never contacts the server, so a deleted User's token still looks valid. Their profile row is gone, `resolveAuthDestination` picks `/onboarding`, and `createProfile` fails there.

### Check the session on load

- In `src/data/auth.ts`, add a function that calls `auth.getUser()` (a server round trip) and reports one of three outcomes: **valid**, **gone** (the server says the User doesn't exist or the token was rejected: an `AuthApiError` with status 401, 403 or 404, or code `user_not_found`), or **unknown** (anything else, such as being offline). Take the auth client as a parameter with `getSupabase().auth` as the default, like the other functions in that file.
- Put the error-to-outcome classification in a pure function in `src/lib/`.
- In `AuthProvider`'s `sync`, when a session arrives for a User whose profile hasn't loaded yet, check it before fetching the profile:
  - **gone:** sign out locally with `signOut({ scope: 'local' })`, because a server sign-out would fail for a User who no longer exists. This clears localStorage and fires the auth change, and the existing `router.invalidate()` in `src/main.tsx` sends the visitor to `/login` with no manual reload.
  - **valid** or **unknown:** carry on as today. Staying signed in when offline is deliberate: only the server saying the User is gone signs them out.

### Sign out from onboarding

- Below the onboarding form's **Continue** button, add a small centred text button, "Not you? Sign out", in the neutral underline style Home used for Sign out before 0.3.0.
- It signs out and goes to `/login`. It has to work for a deleted User too, so when the normal sign-out fails, fall back to `signOut({ scope: 'local' })`. Put that fallback in `src/data/auth.ts`'s `signOut`, so the drawer's Sign out gets it as well.

- [ ] `package.json` version is `0.3.4`
- [ ] A deleted User who reloads the app lands on `/login` with their stored session cleared, without reloading again
- [ ] Being offline on load doesn't sign anyone out
- [ ] Onboarding shows "Not you? Sign out", which signs out to `/login`, including for a deleted User
- [ ] Unit tests for the classification: valid, each "gone" case, and a network error as unknown
- [ ] Integration test against local Supabase using `createTestUser`, `signInAs` and `deleteTestUser` from `src/test/harness.ts`: the check reports **valid** before deletion and **gone** after, and the fallback sign-out clears the session for the deleted User

**Out of scope:** Detecting a deletion while the app is already open (it's caught on the next load or the next failed token refresh); any change to how the Super admin deletes Users.
